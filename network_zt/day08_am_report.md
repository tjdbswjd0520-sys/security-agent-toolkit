**A — 포트 노출 설정 점검**
- **유형:** 접근통제 설정 차이 및 외부 노출 위험
- **근거:** `closed-web-8081`은 `127.0.0.1:8081->80/tcp`로 로컬에만 바인딩되어 있고, `내주소` 접속에는 응답이 없었습니다. 반면 `open-web-8082`는 `0.0.0.0:8082->80/tcp` 및 `[::]:8082->80/tcp`로 모든 IPv4·IPv6 인터페이스에 바인딩되어 있었고, 응답 코드는 `200`이었습니다.
- **먼저 할 일:** 관리용 서버라면 로컬 바인딩을 적용하고, 불필요한 외부 포트 노출을 제한합니다. 비밀번호 노출 여부와 실행 사용자 권한도 확인합니다.

**B — 잘못된 포트 연결**
- **유형:** 서비스 설정 오류
- **근거:** `wrongport-web-8084`는 `Up` 상태였지만 `PORTS`가 `0.0.0.0:8084->8080/tcp`였고, 접속 결과는 `000`이었습니다. `docker logs`에는 시작 로그만 있고 HTTP 요청 기록은 없었습니다. 반면 `compare-web-8085`는 `0.0.0.0:8085->80/tcp`로 연결되어 HTTP `200`을 반환했습니다.
- **먼저 할 일:** 컨테이너의 실제 서비스 포트를 확인하고 `-p 8084:80`으로 수정한 뒤 접속 결과와 로그를 재확인합니다.

**C — 연속적인 경로 탐색**
- **유형:** 의심스러운 경로 탐색 및 접근통제 점검 대상
- **근거:** `2026/10/21 02:44:29`에 `172.17.0.1`에서 `/admin`, `/login`, `/.env`, `/wp-login.php`, `/backup.zip` 요청이 연속으로 발생했습니다. `curl/8.21.0`이 사용되었고 해당 경로들은 `404`, `/index.html`은 `200`을 반환했습니다.
- **먼저 할 일:** 해당 컨테이너의 용도와 테스트 출처를 확인하고, 필요한 로그를 보존합니다. 민감한 파일의 웹 노출 여부를 점검하고 불필요한 경로 접근을 차단합니다. 출처가 확인되기 전에는 실제 공격으로 단정하지 않습니다.
