## 4교시 · 4과목 총정리: 상황마다 원인과 고치는 방법 정리하기

### 문제 4-1 · 상황 8개의 원인과 고치는 방법을 내 말로 정리하기

**상황 정리** — 상황 1 · 2 · 3 · 4 · 7 · 8 중 4개 이상 씁니다. 상황 5 · 6 은 본보기입니다.

#### 상황 1 · 설정 파일 주소를 연달아 요청했는데 「의심」이 아니라 「오류」로 분류됨
- 원인: 규칙 문제입니다. is_suspicious는 HTTP 상태 코드가 401 또는 403이거나 주소에 /admin이 포함된 경우만 의심으로 분류합니다. /.env, /wp-login.php, /phpmyadmin은 모두 404이기 때문에 의심 조건에 해당하지 않고 오류로만 분류됩니다.
- 고칠 파일: log_classify.py (is_suspicious)
- 어떻게 고치나요:조건을 추가합니다. 설정 파일이나 관리자 도구를 찾는 데 자주 사용되는 /.env, /wp-login.php, /phpmyadmin 등의 경로를 의심 경로 목록으로 만들고, 요청 주소에 해당 경로가 포함되면 의심으로 분류하도록 수정합니다.
- 고친 뒤 확인:198.51.100.90의 세 요청이 모두 오류가 아닌 의심 목록에 들어가는지 확인합니다.
- 담당자가 가장 먼저 할 일(선택):해당 IP에서 요청한 시간과 주소를 확인하고, 실제 설정 파일이나 관리자 페이지에 접근을 시도했는지 조사합니다.

#### 상황 2 · 로그 30줄이 이벤트 28개가 됨
- 원인:데이터 처리 문제입니다. normalize_web 함수가 큰따옴표가 2개보다 적은 줄을 깨진 로그로 판단하고 None을 반환합니다. 이 때문에 로그 파일의 30줄 중 2줄이 정규화 과정에서 제외됐습니다.
- 고칠 파일:log_normalize.py (normalize_web의 깨진 줄 검사)
- 어떻게 고치나요:제외된 로그를 확인할 수 있도록 수정합니다. 깨진 줄을 무조건 버리지 말고 별도의 오류 로그 파일에 저장하거나, 원본 줄과 제외 사유를 기록하도록 합니다. 정상적으로 해석할 수 있는 줄은 가능한 한 이벤트로 변환합니다.
- 고친 뒤 확인:원본 30줄 중 정규화된 이벤트 수와 제외된 줄 수의 합이 30인지 확인합니다. 제외된 2줄도 별도로 확인할 수 있어야 합니다.
- 담당자가 가장 먼저 할 일(선택):제외된 로그 2줄의 원본 내용을 확인해 실제 로그 형식이 깨진 것인지, 정규화 함수의 검사 조건이 너무 엄격한 것인지 조사합니다.

#### 상황 3 · 웹 서버 로그에서 사용자를 알 수 있는 요청이 1개뿐
- 원인:데이터 연결 문제입니다. make_ip_user_map은 성공한 SaaS 로그인 기록만 IP와 사용자 이름으로 연결합니다. 203.0.113.50에서 발생한 로그인 실패 5번은 성공 기록이 아니므로 사용자 연결 정보에 포함되지 않습니다.
- 고칠 파일:correlation.py (make_ip_user_map, attach_user_to_web)
- 어떻게 고치나요:IP와 사용자를 연결하는 기준을 보완합니다. 성공한 로그인뿐 아니라 로그인 실패 기록도 활용할 수 있도록 하고, 로그인 시도에 사용된 사용자 정보와 IP를 연결합니다. 다만 실패한 로그인은 실제 계정 소유자가 해당 사용자라고 확정할 수 없으므로 추정 정보로 구분해야 합니다.
- 고친 뒤 확인:웹 서버 로그의 실패 요청 13개 중 사용자 정보를 연결할 수 있는 요청이 늘어나는지 확인합니다. 특히 203.0.113.50의 로그인 실패 5건이 어떤 사용자 계정으로 시도됐는지 확인합니다.
- 담당자가 가장 먼저 할 일(선택):203.0.113.50에서 발생한 로그인 실패 5건의 로그인 요청 내용과 SaaS 로그인 기록을 대조합니다.

#### 상황 4 · 두 로그에 나오는 seoyeon 이 연결되지 않음
- 원인:시간 범위 설정 문제입니다. find_chains는 한 사용자의 가장 빠른 이벤트부터 가장 늦은 이벤트까지의 전체 시간이 60분 이내여야 서로 다른 로그를 연결합니다. seoyeon은 SaaS와 서버 로그에 모두 등장하지만 전체 이벤트 시간 차이가 555분이므로 연결 조건을 만족하지 못합니다.
- 고칠 파일:correlation.py (find_chains)
- 어떻게 고치나요:시간 연결 기준을 보완합니다. 모든 이벤트의 처음부터 마지막까지를 비교하는 대신, 가까운 시간에 발생한 이벤트끼리 묶어 연결하도록 수정합니다. 예를 들어 60분 이내에 발생한 이벤트를 하나의 사건으로 묶고, 시간 차이가 큰 이벤트는 별도 사건으로 관리합니다.
- 고친 뒤 확인:seoyeon의 SaaS 로그와 서버 로그에서 60분 이내에 발생한 이벤트가 연결되는지 확인합니다. 기존에 연결됐던 gaeun의 결과가 유지되는지도 확인합니다.
- 담당자가 가장 먼저 할 일(선택):seoyeon의 로그인, 파일 다운로드, 정산 조회 및 권한 변경 실패가 실제로 어떤 순서로 발생했는지 시간순으로 조사합니다.

#### 상황 5 · 협력사 사무실에서 접속한 정상 접속에 알림이 남 (본보기)
- 원인: 규칙 문제입니다. `SaaS 평소와 다른 IP` 규칙은 지난 접속 기록에 없는 IP 이면 모두 알림을 냅니다. 협력사 사무실 IP 203.0.113.80 에서 jiwoo(A4)와 seoyeon(A5)이 출장 · 외근 중에 접속했는데, 조사해 보니 모두 정상 접속이었습니다.
- 고칠 파일: `tuning.py` (`TRUSTED_IPS` 와 `apply_exception`)
- 어떻게 고치나요: 새로 넣고 뺍니다. 믿는 IP 리스트에 `203.0.113.80` 한 개를 넣고, `SaaS 평소와 다른 IP` 규칙의 알림 가운데 그 IP 에서 온 것만 알림 표에서 뺍니다. 다른 규칙의 알림(A3 · A6)은 같은 IP 여도 빼지 않습니다.
- 고친 뒤 확인: 오탐이 4개에서 2개로 줄었는지 보고, 빠진 알림 가운데 진짜 문제(`real` 이 `True`)가 0개인지 봅니다.
